# 第一轮可靠性改进与验证记录

验证日期：2026-10-24（Asia/Shanghai）。本轮针对 FlowTrail 自有问卷场景；没有重写 Skyvern 执行引擎。

## 解决的问题

| 原有问题 | 本轮实现 | 验证方式 |
| --- | --- | --- |
| 默认分支推送未触发原有 CI 的 push 检查 | 独立的 FlowTrail checks 覆盖 `codex/flowtrail`、`main` 和 PR | 检查工作流配置，在本地执行对应测试与构建；远程结果需推送后查看 |
| 刷新丢失运行入口 | URL 保存运行与会话引用，刷新后仅查询已有运行 | 组件重新挂载测试，断网和无效引用测试；断言没有新的创建请求 |
| 创建结果未知时缺少持续提示 | 仅有会话引用时保留未知状态并引导核查 Runs | 模拟创建失败和会话引用恢复 |
| 模型返回 completed 不等于填写正确 | 分别验证模型状态、实际 DOM 字段与提交回执 | 本地真实浏览器运行及评测器负例测试 |
| 不同测试可能互相影响回执统计 | 使用独立 case ID 关联观测和回执 | 夹具服务隔离测试、不同 case 证据拒绝测试 |
| 任意 terminated 都可能被误判为正确停止 | 必须有 `MISSING_INFORMATION`，原因指出邮箱且实际邮箱为空 | 错误原因、伪造邮箱与无关终止的负例测试 |

## 设计边界

- URL 只保存运行引用与请求模式，不保存填写资料。后端继续负责访问鉴权；修改 URL 不会授权提交或重建任务。
- 恢复运行引用不等于恢复浏览器会话寿命，也不等于后端幂等创建。创建结果未知时仍需要人工检查。
- DOM 观测来自可控夹具，提交证据来自夹具服务，不依赖模型声称“已经完成”。这不是适用于任意网站的审计或强制提交拦截机制。
- 原有上游工作流保留，新工作流专门验证 FlowTrail 场景；本轮没有宣称整个上游仓库的回归检查通过。

## 面试讲解入口

可以围绕“如何避免 Agent 评测假阳性”展开：先展示只有模型状态的旧断言，再展示 DOM 字段、服务端回执和结构化终止原因的交叉验证，最后用负例说明为什么错误选择或错误终止不能算通过。
